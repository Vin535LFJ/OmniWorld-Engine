# 面试叙事（interview narrative）

> **这是什么**：把 `problem-log.md` 的踩坑记录，蒸馏成**面试时能讲的故事**。单文件累积，按阶段追加。
> **谁写**：AI 起草，**owner 用自己的话确认**（W02 步骤 4 的第二个检查点）。
> **为什么单独一个文件**：面试前你只需要打开这一个文件，不用在 5+ 条 problem-log 里现拼故事。
>
> **挑选标准**（重要）：优先**反直觉、能体现判断力**的条目，而不是技术名词堆砌。
> 面试官分辨"真做过"和"背过"的方式，是听你怎么描述**决策过程**，而不是你用了什么工具。

---

## 格式（每条一个 STAR）

```markdown
### <一句话标题：这个故事的钩子>

- **情境（Situation）**：当时的约束与背景是什么？
- **任务（Task）**：你要解决什么？
- **行动（Action）**：你具体做了什么决定？**为什么否掉其他选项？**
- **结果（Result）**：可验证的结果是什么？（数字 / 文件路径 / 提交号）
- **一句话提炼**：这条经验能迁移到哪类问题？
```

**写作纪律**：
- 结果必须**可验证**（有提交号、有文件、有数字）。没有证据的故事不要写进来。
- 行动部分必须写**被否掉的选项**——这是判断力的证据。
- 不要写"我使用了 X 技术"；要写"我为什么选 X 而不是 Y"。

## 阶段 A（核心引擎重建）

### 1. 确定性测试在空实现下"平凡通过"

- **情境**：引擎的核心主张是"同 seed 逐字节复现"。我为它写了确定性断言：同 seed 跑两遍，状态哈希必须相等。
- **任务**：切片 01 红相位（实现故意留空）应该全部失败。
- **行动**：跑下来 8 处断言失败，但 `hash(wa) == hash(wb)` 这条**居然通过了**。定位：两个空实现的世界状态都是空的，哈希当然相等——**"同输入同输出"在实现什么都不做时天然为真**。决定：把测试改成**行为断言与确定性断言成对出现**——`tick==10 且 pos==2.5`（证明它动了）与 `hash 相等`（证明它可复现）缺一不可。
- **结果**：红相位同时暴露两者（行为失败、确定性平凡通过），绿相位同时转绿才可信。记录于 `docs/design/problem-log.md` 002。
- **一句话提炼**：**不变式断言必须搭配进展断言**——数学上，不变量在零状态下总成立。任何"每次结果都一样"的测试，要么配一个"结果确实变了"的测试，要么它什么都不守护。可迁移到幂等性测试、缓存命中测试、序列化往返测试。

### 2. 兼容性疑虑用一次降级实验终结，不用观点辩论

- **情境（Situation）**：白纸重建定 C++20 后，owner 两次提出兼容性疑虑——"很多项目还在用 C++11，很少用 C++17/20"。
- **任务（Task）**：回答"C++20 会不会导致兼容性差"。这不是立场问题，是关于这个代码库的事实问题。
- **行动（Action）**：做降级实验而不是辩论——把 CMake 的 `CXX_STANDARD` 从 20 改到 17 重建：一次通过、ctest 全绿；改回 20 再验：同样绿。同时核查代码实际只用了 C++11 级设施（struct/enum class/uint64 算术/模板）——"C++20"只是工具链的一个设置，不是代码的依赖。**被否选项**：无脑降标准换一个"兼容姿态"（丢掉已验证工具链，且没有任何消费者层面的证据支持降级）。决定：保留 C++20 设置 + boring-core 纪律，结论落 problem-log。
- **结果（Result）**：problem-log 003 + 提交 `3011cd0`；0 行代码修改即可双向编译。
- **一句话提炼**：兼容性争议用**降级实验**回答（改一行、编一次、跑测试），不用观点争论；"设置里选的版本"与"代码实际依赖的特性"是两件事。

### 3. 聚合指标会被"产量最大"的分量绑架

- **情境（Situation）**：阶段 A 收口的 Gate-1 对齐运行里，判据 (c) 要求指标能区分"正常模型 vs 故意注入错误置信度的模型"，但在环两组检测器的 ECE 几乎一样（0.4977 vs 0.4963）。
- **任务（Task）**：解释判别力为何消失——是指标算错了，还是别的东西错了。
- **行动（Action）**：定位到聚合 ECE 被**产量**淹没：一轮 9746 条便签里世界模型占 9600 条（固定 0.5 置信度、准确率≈1），每条贡献 ~0.5 的 |acc−conf| 项，把检测器 ~300 条的真实差异彻底淹掉。**被否选项**：① 改指标公式——错的方向，问题在聚合不在公式；② 把检测器置信度公式调到"好看"——那是对合成场景过拟合。决定：per-producer ECE 排期阶段 B（pre-rebuild 的报告本来就是按 producer 分表的——旧设计防的正是这个坑），并把教训升格为通用规则：**聚合指标必须附按来源分解的视角**（workflow-manual 反模式 #13）。
- **结果（Result）**：problem-log 005 + 对齐报告 Findings F1；机制级判别仍然精确（单元测试：诚实组 ECE == 0.0 vs 夸大组 == 0.125，全二进制精确）。
- **一句话提炼**：**任何"全体平均"型指标都要同时保留"按来源分解"的视角**——平均误差、平均延迟、总分，都会被配额最大、信息最少的分量变成主角。迁移场景：把"平均响应时间"当性能判据的压测报告。

### 4. 门卫拦下了它自己的作者——两次

- **情境**：阶段 B 的实现期，我为仓库装了 pre-commit 门卫（测试 + 文档图 lint + 产物卫生），本意是防未来的 AI 会话犯机械错误。
- **任务**：连续写 B2/B3 两份详细设计文档，各自带一张 Mermaid 时序图。
- **行动**：提交两次都被自己的 lint 拦下——一次图里残留 ASCII 花括号（`run（models={...}）`），一次消息文本带半角括号。**没有绕过，没有关 hook**：按错误行号改写法、重跑 lint、再提交。**被否选项**：`--no-verify` 跳过（10 秒的事，但跳过一次就会跳过第二次）；把 lint 规则放宽迁就自己的图（那是让门卫适应作者，不是作者适应门卫）。
- **结果**：B2/B3 均在修正后入库（236e9f6 / 85e3cd6）；GitHub 渲染零报错；此后每份设计图先过 lint 再进提交。提交 `4cf6740` 的工具链 + 两次记录。
- **一句话提炼**：**Guardrail 的价值在拦住作者自己时才兑现**——机械错误的最高发人群不是粗心的新人，是赶进度的作者本人；把检查放在提交路径上，比放在"记得要检查"的脑子里可靠一个数量级。
